## Findings

### [BUG] `experiments/checkpoint-external-validation/run.py:752-817,1278-1293`; `REPORT.md:53-55` — Reused teacher predictions are attributed to source/runtime that did not produce them

`teacher_cache_identity()` binds the external manifest, teacher artifact,
prefixes, short-clip policy, and a prediction-space label. It does not bind the
producer's driver/imported-source hashes, package/runtime versions, ordered
language-to-teacher-index mapping, or inference implementation. The read path
checks only the cache's self-hash, that incomplete identity, and five vector
lengths; it trusts the cached summary and `teacher_identity` without
recomputing or validating their semantics.

The publication run actually took this path (`teacher.cache_audit.reused=true`).
Its experiment identity binds the *current* `source_at_start`, but does not bind
the reused cache hash or a producer identity; the package environment is stored
only outside `experiment_identity`, after the run ID is computed. Consequently,
a cache produced before a change to `evaluate_teacher`, `label_indices`, the
language mapping, or a numerical dependency can be reused and then reported
under the new source hash and the same semantic experiment identity. A
self-consistent stale cache can also change every reported teacher control
number without changing the run ID.

The current cache was created minutes before publication and its 700-by-five
vectors are internally well formed, so this finding does not prove that the
published 70.24% teacher composite is wrong. It proves that the claimed
provenance is not established. Bind a cache-producer identity containing the
pre-import staged source, exact runtime/dependencies, ordered language/index
mapping, and all inference settings; validate values and recompute summaries
from retained raw predictions on reuse. Bind the accepted prediction/cache
digest into `experiment_identity`, and add a regression proving that a source
or generator change invalidates the cache.

## Interview questions

1. **Why keep both an exact manifest hash and a canonical-record hash?** The
   exact hash names the bytes actually read and detects whitespace/encoding
   generation changes; the canonical hash proves semantic record equivalence.
   Requiring both prevents different consumers from silently choosing
   different valid views.
2. **Why are later manifest pathname reads still allowed?** They are drift
   alarms only. Every consumer already holds defensive records from the one
   immutable launch snapshot, so a later read can abort publication but cannot
   change the generation that trained/scored the model.
3. **Why is the external reject verdict robust to the reported bootstrap flaw?**
   Step 800 gains only 0.38 pp and independently fails the predeclared 2 pp
   effect-size gate. Both the stored interval and prompt-clustered reanalyses
   include zero, and every candidate has zero worst-language recall.
4. **What provenance does the ECAPA cache currently fail to prove?** It proves
   its payload is self-consistent and names the manifest/artifact/constants,
   but not which evaluator source, label mapping, packages, or runtime produced
   those predictions. The publication run instead records the current source,
   which may merely be the consumer.
5. **Why did the run/checkpoint hashes change while the model-state hash did
   not?** Schema 4 adds the exact manifest generation and schema-5 target/source
   evidence to the content identity. Deterministic retraining reproduced the
   same weights, but the enclosing provenance bytes and serialized checkpoint
   necessarily changed.
6. **What can be said about CPU speed now?** All three opportunistic processes
   ran faster than real time, but their medians span 0.00584--0.08833 RTF.
   Until fresh processes run under a controlled affinity/thread/load contract,
   no single reciprocal is a reproducible host speed factor.
