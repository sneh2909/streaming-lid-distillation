## Findings

### [BUG] `src/streaming_lid/throughput.py:17,120-188` — Incomplete rows can mint a protocol-compliant speed headline

`aggregate_processes()` requires only seven rows, ten positive timing values
per row, contiguous indices, and equality of any non-empty `binding` mapping.
It never checks `EXPECTED_WARMUP_SWEEPS`, `full_corpus_warmups`, warm-up output
digests, the required binding keys/types, per-sweep records, or agreement
between the summary arrays and those records. `protocol_compliant` at lines
149-152 is therefore only a process/sweep-count check, despite feeding
`throughput_stability_passed`, `x_realtime`, and
`scalar_speed_headline_permitted`.

An exact probe with seven rows, `binding={"placeholder": true}`, ten constant
wall/CPU values, and no warm-up or sweep-diagnostic fields returned:

```text
protocol_compliant=True
identity_bindings_equal=True
throughput_stability_passed=True
scalar_speed_headline_permitted=True
x_realtime=100.0
expected warmups constant=2; row warmup evidence=False
```

The normal coordinator enforces its CLI counts and generates rows itself, so
this does not prove the pending real run is numerically wrong. It does mean the
module's advertised pure validation and any later artifact revalidation can
approve a forged/incomplete protocol. Validate an exact versioned binding
schema; require two matching warm-up digests; require ten indexed sweep records
whose clocks, RTF arrays, affinity/thread observations, and output digests
recompute; and derive `protocol_compliant` only from that complete validation.

### [METHOD] `scripts/benchmark_throughput.py:481-498,511-516,704-710` — The timed scope silently includes output verification and hashing

`measure_dual_clock()` wraps `one_sweep()` in full. In addition to log-mel and
student replay, `one_sweep()` performs `torch.isfinite(...).all()`, detaches and
materializes every logit tensor, converts shapes to canonical JSON, converts
all logits to NumPy bytes, and updates SHA-256 with IDs, dtype, shape, and
content. Those operations occur before both clocks stop. The published
`includes` list names frontend, scheduler/allocation, overlap recomputation,
and student forward, but not the output scan/serialization/hash pass.

The digest is valuable correctness evidence, but it is not part of the named
`offline_replay_frontend_student_wall_rtf` workload and was not part of the old
evaluator's replay body. Either stop the clocks before verification (while
retaining enough outputs to validate afterward), or explicitly rename and
document the broader metric. Do not compare this number directly with the old
process-local RTF until both execute the same timed body.

### [DEFEND] `scripts/benchmark_throughput.py:206-225,690-698,783-818` — Publishing one run changes the identity of an otherwise identical rerun

The input-stage root includes the complete pre-benchmark `summary.json` hash,
and that root is included in `benchmark_identity`. Publication then adds
`controlled_throughput` to the same summary. A second invocation with identical
checkpoint, audio, source, machine, and protocol therefore captures a new base
summary hash, input-stage root, and benchmark ID solely because the previous
benchmark pointer exists. This preserves lineage and does not corrupt the
first result, but it is awkward to defend as a workload identity. Prefer an
immutable release-identity subset (or canonical summary with the controlled
pointer excluded) and keep observation/result IDs separate and append-only.

## Interview questions

1. **Why are 70 timed sweeps not 70 independent replicates?** Ten sweeps share
   one process's allocator, caches, thread pools, and host episode. Collapse to
   one median per fresh process, so the outer sample size is seven.
2. **What is wrong with checking only that every binding dictionary is equal?**
   Seven equally incomplete dictionaries prove equality, not presence or
   validity of source, input, output, affinity, threading, or warm-up evidence.
3. **Why use both wall and process CPU clocks?** Wall RTF is deployment-facing;
   process CPU time helps distinguish waiting/pre-emption from increased CPU
   work, without by itself identifying a cause.
4. **Why is output hashing inside the clock a scope problem?** It adds a second
   scan, materialization/serialization, and SHA work not performed by the
   deployed student and not named by the metric, so comparisons use unlike
   workloads.
5. **What do the two English-teacher progress rows establish?** Only that
   Whisper fixes the sampled English cases while losing substantial broader
   held-out accuracy and costing about 9x ECAPA wall RTF in this incomplete
   diagnostic. They do not establish a global teacher replacement.
