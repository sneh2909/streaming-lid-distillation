## Findings

### [BUG] scripts/train.py:214-223,371-384 and src/streaming_lid/run_identity.py:71-82,203-222 — The run identity is sampled after training, not at launch

DistillationDataset preloads the launch audio, features, and targets before optimization, and Python has already imported the launch source. Only after all 1,600 updates does build_run_identity reread pipeline files, manifest/audio bytes, and target metadata from disk. If any of those paths changes during training, the model still trains on its preloaded launch tensors/code while its checkpoint identity binds the later bytes. Evaluation will accept that internally consistent but historically false hybrid.

A concrete race is: load audio A at line 217, replace the referenced WAV with B while the loop runs, then corpus_identity hashes B at line 371. The checkpoint claims B even though every optimizer step used A. The same issue applies to imported source and target metadata.

Capture and validate a complete dependency snapshot before dataset preload, build the final identity from that immutable launch snapshot plus the final model hash, and rehash/equality-check every live dependency before publication. Abort if anything changed.

### [METHOD] scripts/teacher_targets.py:143-155,199-228 — Main switch targets still use unavailable future anchors

The teacher runs every 25 frames, then np.interp blends each anchor with the next. A target immediately after anchor a therefore consumes anchor a+25, whose own window extends 250 ms past that later frame. Ordinary targets have 260-490 ms of future evidence even though the aligned student has 250 ms; only exact anchor frames meet the stated horizon.

On the regenerated current cache, 2,295/2,394 switch frames (95.86%) consult a future anchor. Replacing interpolation with previous-anchor hold changes the raw top class on 215/2,394 frames (8.98%); KL(linear || hold) is 0.12276 on average and 0.72942 at p95, with maximum posterior-coordinate change 0.84107. The main run correctly labels this result latency-invalid, but it still trains on the mismatch.

Use previous-anchor hold, dense calls, or a hop explicitly reserved inside the availability budget. Store/assert each target's latest source sample. Regenerate targets, checkpoint, and evaluation after the change.

### [METHOD] experiments/target-type-ablation/run.py:763-854,1210-1265, experiments/teacher-window-audit/run.py:394-488, and experiments/teacher-anchor-hop-audit/run.py:288-377 — Boundary matchers can manufacture a transition from the interior of a run

The teacher audit matcher tries every index rather than only true run starts. A target run that starts much too early can first be marked premature, then be accepted again from an interior index near the reference boundary. Its source arm can also occur anywhere earlier and remains armed forever. An actual probe with a source run at 0.025-0.525 s, one continuous target run beginning at 0.775 s, a 4.0 s boundary, 250 ms lookahead, and 500 ms stability reported premature onset 0.775 s but also detected=true with a manufactured onset at 3.775 s and confirmation at 4.275 s.

The target-type persistent_transition has the related chronology gap: the source may arm after the reference boundary, boundary matching checks only target start/confirmation, and policy_transition_detected counts every non-null commit without any reference match. A wrong-source excursion followed by source recovery and target can therefore pass.

Score actual run boundaries in chronological order, require source acquisition before and adjacent to the annotated event, and match one real direction-specific transition under an explicit early/deadline policy. Current target-type arms detect 0/2 transitions, both teacher audits have no actual premature target run, and the anchor-hop rejection independently fails KL/disagreement gates, so the published reject decisions remain unchanged.

## Interview questions

1. **Why can a content hash still describe the wrong training run?** A hash proves which bytes were sampled, not when. Hashing live paths after preloading/training can bind later bytes; the dependency snapshot must be captured at launch and checked again before publication.
2. **Why does 250 ms future at each teacher anchor become as much as 490 ms for a 10 ms target?** Linear interpolation just after anchor a uses anchor a+250 ms, and that later anchor itself reads 250 ms ahead. Relative to the earlier frame, the endpoint is roughly 490 ms.
3. **What distinguishes a real switch from an interior point in a persistent run?** A switch is a class-run boundary with a valid pre-boundary source state and a chronologically matched target run. Rescanning every interior frame can fabricate an onset near any desired reference time.
4. **Why reject the 50 ms anchor hop even though its switch onset is within 40 ms of dense calls?** It still has p95 KL 0.1189 and 4.14% non-collar top-1 disagreement, both beyond the predeclared 0.10/2% gates; matching two crossing times is insufficient trajectory fidelity.
5. **What does atomic corpus publication guarantee?** A failed build cannot change the release manifest; immutable content-addressed WAVs are installed first and the manifest pointer swaps last. It may leave an unreferenced new object, but the prior manifest and referenced bytes remain valid.
6. **Would extending student history from 1.075 s to 1.755 s fix switch latency?** Not the teacher floor. It may reduce student-teacher fidelity error, but the dense teacher trajectory itself is about 1.26 s late on these fixtures, so any gain must be measured as student excess above that floor.
